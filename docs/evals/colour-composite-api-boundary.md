# Prepared colour composite: API boundary

Prepared 1 November 2026 from current official OpenAI documentation. **No API
call was dispatched.** This module is callable transport, not an authenticated
route, permission grant, ledger or accepted visual result. The native composite
is still awaiting the owner's judgement. Its acceptance and root's dispatch
decision precede enabling the future dynamic path.

## Fixed request and interface

`editColourComposite({key,sources,fetcher?})` in
[the provider](../../lib/colour-composite-provider.mjs) takes **exactly four**
`{bytes,mimeType,lightingRole}` records in source order. Roles are `daylight`,
`indoor-colour-cast`, `supporting` or `unknown`; they are supplied from evidence,
never inferred from an account's identity. For dynamic judge cases use `unknown`
when lighting is not established. No arbitrary prompt, URL or filename input.

Before dispatch, it checks count, byte caps, declared/decoded format, single-image
content and a 16-megapixel decode limit. It decodes/orients each input, resizes
within 1024×1024 without upscaling, re-encodes JPEG and strips source metadata.
Resizing/re-encoding can lose fine detail; it is an operational input bound, not
colour calibration. Original private photos remain unchanged.

The request pins `gpt-image-2.5-sunburst-2026-09-08`, four multipart `image[]`
parts, `n=1`, `quality=medium`, `size=1024x1536`, `background=opaque` and PNG output.
The official [model page](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst)
identifies that snapshot and recommends Sunburst where editing precision matters.
The [edit endpoint](https://developers.openai.com/api/reference/resources/images/methods/edit)
documents multi-image input, these request options and base64 output; its example
uses repeated `image[]` multipart fields. We use a narrower four-image cap than
the endpoint's supported maximum.

The fixed generic prompt carries the private native experiment's **intent**:
preserve likeness, regional anatomy, asymmetry, ordinary skin variation, hair and
existing clothes while estimating diffuse neutral light. It contains no private
personal-case notes, account identifiers or expected colour-season target. It
does not promise identity fidelity or calibrated complexion truth. Every returned
portrait must enter the saved reference lifecycle as **pending**, with the actual
source media IDs and provenance `api`; it must not inherit another version's
approval or become the mirror reference before explicit user approval.

Return: `{image,contentType,requestId,model,modelSource,usage,pricingVersion}`.
Only bounded whitelisted usage counts and a validated request ID/model survive.
Missing usage stays `null`; a missing reported model is labelled `requested`.
Provider prompts/errors and source images are not telemetry. Generated bytes must
decode as one 1024×1536 PNG before being returned.

## Pricing: estimate, not an official hard bound

Pricing version: `openai-standard-2026-11-01-image25-v1`. The official
[Standard pricing table](https://developers.openai.com/api/docs/pricing) gives
$5/M text-input tokens, $8/M image-input tokens and $30/M image-output tokens.
The Image API path gets no assumed cache discount. At these rates, an engineering
scenario of 10,000 text-input + 100,000 image-input + 30,000 image-output tokens
costs $1.75. The module exposes a padded **$2.00 reserve estimate** (2,000,000
microUSD), not observed consumption or an enforced provider maximum.

The official model page explicitly says the GPT Image 2 calculator does **not**
estimate GPT Image 2.5 token consumption. The
[generation guide](https://developers.openai.com/api/docs/guides/image-generation)
also describes token-based cost estimation. No source inspected establishes a
strict total-token ceiling for this fixed 2.5 edit request; the 100k/30k scenario
is our conservative planning assumption, not an official guarantee. Accordingly,
`COMPOSITE_PRICING.hardBound` is `false`. Root must resolve a suitable conservative
reservation/overage policy before dispatch; this estimate alone cannot prove
enforcement of the total USD50 allowance. Do not substitute older per-image
output prices as the total four-input edit cost.

## Failure, retry and integration boundary

There is exactly one HTTP attempt, a 180-second abort deadline and **no automatic
retry**, including 429/5xx. Local validation failures have `dispatchStarted=false`.
Once fetch is attempted, timeout, connection loss, malformed response, provider
error or invalid output all carry `dispatchStarted=true`; these may have consumed
money. Preserve request ID and reported usage when available, retain the ledger
reservation as uncertain where appropriate, and reconcile before an explicitly
authorised new attempt. Do not release an uncertain charge as if it were zero.

Root's future server route owns active authentication, same-origin protection,
source ownership/readiness/consent, applicable cohort allowance and total-budget
reservation, concurrency/idempotency, dispatch eligibility, private storage and
pending reference registration. Calling this module directly bypasses those
controls. No top-level side effects, environment-key lookup or dispatch-on-import
exist here. Account model access, live response shape, latency, actual cost and
likeness/colour fidelity remain unverified until an authorised live trial.

Local verification used synthetic small source PNGs and an injected fetcher;
it checked four multipart inputs, fixed model/count/quality, decoded portrait
output, usage whitelisting, invalid source/count rejection before fetch, and
single-attempt connection-loss/429 handling. No network/API request was made.
TypeScript, focused ESLint and whitespace checks passed. These checks establish
transport behaviour only, not live API compatibility or image quality.
