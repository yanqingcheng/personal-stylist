## R1 — Deliberately small architecture

One Next.js App Router app on Vercel, React/TypeScript/Tailwind. Supabase Auth + Postgres + private Storage. Server route handlers own all spending and inference. Use the official OpenAI SDK and Zod validation. No Redis, general workflow engine, vector database, microservices, or universal style ontology for this hackathon.

Suggested boundaries: `features/colour` (pure factors, atlas, trial state), `features/style` (regional/holistic evidence and rounds), `features/editorial`, `lib/server/access`, `lib/server/credits`, `lib/server/media`, `lib/server/provider`, `lib/server/profiles`. Server modules must not enter client bundles. Supabase SQL migrations and transactional functions are source controlled. Use one deploy/migration owner; no simultaneous schema writers.

Routes: public `/`, `/colour-system`, `/login`; gated `/profile`, `/colour/start`, `/colour/drape`, `/colour/refine`, `/colour/result`, `/style`, `/editorial`. Render unavailable stages as honest explanations rather than active dead actions. Auth return URL must be allowlisted, never an arbitrary client-supplied redirect.

## R2 — Accounts and invites

A user signs in, then redeems a phrase to activate access. Show both steps as one short entry flow. Auth users without a redemption have no AI or profile/media creation permission. The 100 cap is on activated attendee accounts, not raw Supabase Auth records or proven unique humans.

Use two independent invite records: attendee hard ceiling100, configured live capacity initially0 until cost calibration; judge capacity default10 (operator configurable). Each uses a memorable four-word phrase. Phrases are meant to be shared; do not demand high entropy or pretend they establish real identity. Normalize trim, lowercase, hyphens to spaces and repeated whitespace; store a SHA-256 digest for simple comparison, not as a claim of strong secrecy. Keep actual configured phrases out of public source so the deployment owner controls distribution. Phrase expiry/revocation controls new activation, not existing sessions; disabling an account is a separate operation.

Proposed initial sign-in: email OTP via configured SMTP. Probe delivery to an ordinary non-team address before choosing it. If configured OAuth is available and email delivery is not, use that supported provider. No disabling email verification, fake addresses, anonymous-account bypass or silent downgrade to shared-session identity. If neither works, keep gated functionality unavailable while other build work continues.

`redeem_invite(phrase)` is a server-only database transaction bound to verified session identity: lock account activation key and invite; check active/expiry; if user already activated return current activation without consuming another slot; check redeemed_count < capacity; insert unique redemption(user_id); increment capacity count; create account allowance and profile shell; commit. A user cannot redeem both phrases to stack allowances or self-upgrade to judge. Operator can promote a known judge explicitly using a documented protected command: no active/uncertain operation; consume a judge slot atomically, retain past spend in its original cohort, do not refund attendee slot; cancel unused attendee allowance and assign future judge allowance only if judge pool capacity supports it. No merging/top-up of both allowances. Judge code grants demo access, never administrative privileges. Handle invalid/exhausted/revoked with clear copy; retain sign-in.

Checks: requests A/B contend for last slot → exactly one succeeds; retry same account → same activation; attendee sold out → judge succeeds; unactivated account can't call AI/upload; logged-out direct calls fail; rotated code stops new activations. Rate-limit phrase attempts per account. Check Supabase venue/shared-IP auth limits before launch; avoid a low whole-venue IP throttle. No email or photo logging.

## R3 — Private data and revisions

Minimal relations:

- `access_grants`: user_id primary key, invite_id, cohort, active, allowance_microusd, reserved_microusd, spent_microusd, editorial_hold_microusd, created_at.
- `invites`: id, digest unique, cohort, capacity, redeemed_count, active, expires_at.
- `profiles`: id, user_id unique (one profile per account initially), revision, analysis_revision, schema_version, current_step, pause_reason, document JSONB, updated_at, deletion_state.
- `media`: id, user_id, profile_id, object_path unique, kind, content_type, byte_size, status, created_at. No external URL supplied by client is trusted as owned media.
- `rounds`: id, user_id, profile_id, parent_round_id, base_revision, status, hypothesis JSONB, feedback JSONB, media_ids, created_at. Append rounds; do not overwrite older generated proposals.
- `ai_operations`: id, user_id, profile_id, kind, idempotency_key, payload_hash, base_revision, round_id nullable, lease_expires_at, client_request_id, state, reserved_microusd, settled_microusd, provider_ref, result_ref, pricing_version, timestamps. Unique(user_id,idempotency_key).
- `budget_pools`: attendee, judge, development; integer limits, reserved and spent. Sum limits <= owner-approved global cap.
- `budget_control`: singleton total_limit_microusd=50000000, reserved, spent, emergency_disabled.
- `access_attempts`: account/time-window/attempt_count for bounded invite retries, updated atomically; short operational retention. Account budgets sit inside the relevant pool.

Enable row-level access on all exposed tables; user may read own profile/media/rounds/operation summaries. Raw budget/invite administration is server-only. Do not permit user writes to grant/cohort/credits, inferred factors, operations or provider refs. Explicit server actions accept whitelisted user edits. Privileged invite/credit RPCs use SECURITY INVOKER with execute revoked from PUBLIC/anon/authenticated and granted only to service_role. Server first verifies user identity, then passes it to the isolated service client; never reuse the cookie-attached user client as the service client. Private-schema helpers, if needed, use fixed search_path. No auth role/cohort authority comes from user-editable user_metadata. Server service keys stay private; never accept a client-provided user_id as authorisation.

Profile JSON records raw answers/quotes, observations, hypotheses, factors/ranges, evidence IDs, contradictions, preferences, selected template, inferred candidates, approval and text that does not fit named factors. Keep model-generated records separate from user statements and timestamps. T/V/C unknown is null, neutral is0; unsupported evidence cannot become certainty. Include atlas/prompt/schema versions.

Save on meaningful actions and debounce free text. Show saving/saved/unsaved; don't advance a paid action until required input is saved. Mutation includes expected_revision; atomic update WHERE revision=expected increments it. Conflict returns409 and latest revision; preserve unsaved local text, offer reload/reapply rather than silent overwrite. Each operation also records a hash of its relevant evidence/reference/template/round inputs. Ordinary saves (step changes, unrelated text) do not invalidate a generation; only a changed relevant-input hash makes it stale. Results with obsolete relevant inputs are retained for inspection, never silently applied. CAS still protects every write; analysis_revision increments on material evidence changes. Changes after approval mark downstream style/editorial stale without deleting history.

Media starts private: propose JPEG/PNG/WebP up to10MB, max4 colour portraits, image decode/dimension validation, strip metadata and normalize orientation once. Document rejected HEIC clearly. First create a server-authorised pending media ID/path with a per-account pending-count and total-storage-byte allowance (defaults:4 pending,100MB stored). Issue upload permission only for that path; forbid overwrite of ready media. Upload directly to an owned Storage path under RLS to avoid routing large files through Vercel request bodies. Finalize only after server verifies object existence/ownership/type/size and decoded image content; provide a protected cleanup command for expired pending uploads, and do not promise automatic cleanup before scheduled; inference consumes owned media IDs, not arbitrary URLs. Same normalized bitmap and transform must appear on both drapes. Signed read URLs are short lived; no public buckets or faces in logs/source.

Delete blocks new operations, removes media and records with retryable progress, then confirms completion. For running calls deletion invalidates application of results; discard late assets and reconcile charges without resurrecting profile data. Keep only minimal pseudonymous spend records necessary to prevent allowance reset, and state this accurately. A deleted profile does not earn fresh credits. Provide sign-out and photo-free export. Choose and publish actual retention behaviour at deployment; do not promise automatic expiry unless implemented.

## R4 — Paid-operation protocol

Budget decision: $50 total. Proposed initial allocation within that cap: development/API calibration $5, judges $10, attendee pool $30, unallocated contingency $5. These are operator-adjustable allocations inside the authorised total, not separate spend authorisations. Start attendee activation disabled until actual costs are measured; 100 is an upper bound. Calibration consumes the development pool and is recorded even before attendee launch. No untracked experiments outside the accounting path. Create an operator-only development access grant on an ordinary authenticated account, mapped solely to the $5 development pool; no public invite or bypass. Crowd activation remains disabled during calibration.

First use the Codex development session for qualitative prompt/data/UI experiments where supported, with private consented fixtures. This is not an application backend and does not establish API capability, cost or latency. Only after qualitative confidence, run bounded metered website/API probes (start with one observation, one board and one revision; stop at $5). If calibration cannot fit that allowance, stop and report; do not consume judges' reserve silently.

Choose the supported model/image settings after measuring billable usage and latency. Define an account package cost bound in actual provider operations: bounded colour reasoning; one initial multi-panel board containing2–3 looks if fidelity allows; two separate one-board revision calls; all LookSpec planning/input-image costs; and one bounded text editorial. If composite fidelity requires separate images, recompute the package using every actual image/call rather than reusing the cheaper composite assumption. That package is only a launch-sizing assumption, never a maximum number of satisfaction iterations. Account allowance can be used differently and cannot guarantee unlimited rounds. Set live attendee capacity to min(100, floor(attendee_pool/package_allowance)); judge capacity similarly fits its pool, initially at most10. If this cannot fund any usable package, do not open signups promising the full journey. Existing account slots are never silently increased by deleting a profile.

Store editorial_hold_microusd: non-editorial admission requires available-request_bound >= hold. Approved editorial may consume the hold; failed-but-billable editorial consumes cost normally and leaves only the unused hold, with honest pending/failure state. Guarantee an opportunity for the first bounded attempt, not limitless free retries. Keep enough of each account allowance for one bounded text editorial after approval; image editorial is optional if funds remain. Reserve cohort concurrency as well as money so crowd requests cannot occupy every known provider slot. Probe shared provider throughput; state that external/provider outages can still affect judges. No fictitious guarantee of instant rendering.


Use integer micro-USD internally. Display a simple remaining allowance; number of moodboard rounds is not a satisfaction rule. Models, image quality/size, input count/bytes and output token limits are server selected. Prompt text and profile content are untrusted data, never permission to call arbitrary URLs/tools or alter credits.

Each paid action has a stable client operation UUID, a server canonical payload hash and immutable input revision. Same key+same payload returns existing state/result; same key+different payload is409. Disable SDK retries for non-idempotent paid calls unless the provider explicitly guarantees deduplication for that operation. Browser reconnect must poll saved status, not create a new generation.

Reserve transaction: verify active grant/owner/feature; validate bounds; lock global/pool/account counters consistently; check available balance against conservative maximum request cost; enforce one in-flight operation per account initially; insert operation and reserve all counters atomically. Fixed model settings and a versioned current price table must make the upper bound credible. If cost cannot be bounded, do not enable that feature. The global cap includes deployment test calls in a separate development pool. A documented protected top-up can move unallocated contingency into a pool/account without increasing the total50USD, with reason recorded; never silently use judges funds. No pool borrows from the judges reserve automatically.

Dispatch once after durable reservation. States: reserved → running → succeeded | failed_before_dispatch | uncertain | rejected_result. Persist provider request ID as soon as available. Exactly-once external execution is not claimed: a process crash after sending may leave an uncertain billable operation. Repeated local dispatch must fail state-transition guard. A server status read or protected reconciliation command turns expired running into uncertain, releases its concurrency slot but holds money; TTL derives from measured timeout plus margin. A reserved operation may be cancelled/refunded only if atomic dispatch transition never happened. Uncertain status remains visible and cannot redispatch under the same key. Keep uncertain reservation held; no blind retry/refund. Operator can reconcile recorded provider status/usage; if not recoverable, conservatively settle reserved amount and allow a clearly labelled user-initiated new attempt. Refund only confirmed unspent allowance. Invalid/refused output may still be billable; retain spend, do not apply invalid output.

Completion settles actual cost once, releasing only unused reserve. Missing usage settles conservatively at reservation bound, not zero. If actual cost exceeds bound, stop further operations globally and investigate; the provider budget is a second backstop, not a replacement for admission control. No known underbounded model configuration is enabled.

A route must await its provider call and persistence within verified platform limits; no fire-and-forget work after HTTP response. For initial deployment use bounded synchronous calls with operation status polling from other requests. Probe real image latency vs deployed duration limits. If images cannot reliably complete, explicitly leave image generation unavailable until a supported durable execution mechanism is implemented; don't pretend a DB job row is a running worker. Bound reads/status polling too.

Check concurrent near-exhausted requests, duplicate clicks/reconnects, timeout after dispatch, invalid output, malicious client model/quantity changes, unauthenticated direct calls, cross-account media/job IDs, and judge-reserved allowance after attendee exhaustion. Budget failure preserves consultation and offers continuation later; never sets approval.

## R5 — Colour and shared profile behaviour

Reference prototype logic only supplies directional evidence: it cannot infer a genuine neutral centre from sign votes. Do not reuse it as a forced exact classifier. Proposed conservative candidate rule: unknown/broad/conflicting axis imposes no exclusion; two coherent independent trials across hue families support a provisional interval [0.10,1] or [-1,-0.10]; these numeric boundaries are design defaults, not calibration. Keep status and raw votes; never assign the midpoint as a measurement. Candidate inclusion uses atlas anchor within every constrained interval; expose broader exploration if none match. Show at most3 comparison options (not ranked “best”): first choose the lexicographically smallest stable atlas ID in the candidate set; then greedily maximize minimum Euclidean anchor distance to selected options on unresolved axes, ties by stable ID. If no axes are unresolved, use all3 axes for diversity. Keep “compare more” for all candidates. This is a deterministic display sampling rule, not a suitability score. All31 remain selectable as explicit user choices. In particular neutral/deep/vivid must remain explorable when temperature evidence is broad, without claiming neutral was established.

Store responses by trial, photo and revision. Keep the latest response per (trial,photo); collapse these into one trial vote only when all directional responses agree. Any opposite directional response across photos marks the trial contextual/conflicting and contributes no direction; any both response marks the trial broad and contributes no direction. Neither/unsure contribute no direction. One both response marks the axis broad rather than forcing centre0; contradictory directional trials similarly leave the axis unconstrained. Other axes remain independent. Two coherent distinct-trial directions and no broad/conflict flag permit the provisional interval; otherwise unknown/broad remains unconstrained. Photo AI offers qualitative hypotheses only at launch and cannot narrow deterministic ranges. Repeated same pairs never become independent votes. Seed random A/B placement once per comparison and store the mapping, so back/reload preserves it and left/right preference does not change evidence.


Follow source atlas and current colour contracts referenced in implementation-plan.md. Quiz answers/self-reports produce hypotheses, not measurements. Eight initial drapes; unknown axes first, then uncertain/disputed factors and distinct hue families. Two coherent directional votes are a tentative signal, not scientific confidence. Both means broad range, neither means unsuitable comparison/context, unsure means no directional evidence, conflicting votes are not neutral.

One source portrait per comparison, user may retry with another lighting source; store photo ID and exact swatches/transform alongside answer. A reference replacement invalidates associated pending computations but retains prior responses with provenance. Current profile may be explicitly revised rather than pretending all photos have identical colour calibration.

Result supports provisional candidate selection: record `selectedTemplateId` as user choice independently from `candidateClassIds` and factor estimates. Taste excludes personal swatches only. If every light shirt colour is excluded, show that gap and offer alternatives; don't silently restore rejected colours or claim a complete personal subset. Keep underlying full template roles/hue families available for comparison. No-response journey yields unknowns and exploration, never a fake personal diagnosis.

## R6 — Joint moodboard consultation

Body/garment and essence hypotheses live in one consultation; no required separate classification funnels. Regional features get concrete names and provenance; no global yin/yang average or mandatory binary per feature. Essence can remain holistic prose with tentative descriptors. Don't turn aesthetic impression into a personality claim. Read menswear/other-adult boundary notes before choosing inventory. Children are out of this hackathon path; any later child essence feature cannot execute adult body analysis.

A required full-body reference is collected at style entry before any claim to depict the user's figure; it is optional in colour-only intake. Without it, continue colour/save, or offer clearly scoped portrait/accessory work as a limited mode, not completion of the body-style journey.

A structured LookSpec precedes rendering: garment IDs/descriptions, construction, palette references, proposed effects, evidence IDs and rendering notes. Validate class/colour IDs and owned media; reject factor changes sourced only from taste or drawing errors. Never send raw user text as instructions to an unrestricted image tool. A proposed garment contradicting a hard rejection must be revised before image spend. Inferred interpretations of free text are shown as “what I heard” and can be corrected.

Style entry requires explicit selectedTemplateId; inferred candidates alone do not choose it. Initial round: propose2–3 coherent alternatives with distinct testable reasoning and chosen palette. Generate each as a realistic diagnostic illustration on the user's references, not a stranger and not a promised virtual try-on. For the first implementation render one multi-panel image per round, containing the2–3 alternatives, after one bounded planning operation. Tie each operation to round_id; save planned LookSpecs before rendering. If fidelity demands separate images, treat this as a calibrated alternate execution mode: one operation per image, aggregate round budget reserved up front, explicit partial status, measured cohort concurrency and resume only missing images under new operation IDs. Do not run three sequential long renders in one route or silently reuse composite pricing. Save hypotheses separately from generated images; image/model failure cannot count as user rejection. Capability probe must test whether fidelity is usable before promising it to attendees.

Feedback supports whole look, item or attribute plus free text; dimensions are perceived harmony, taste, willingness to wear and rendering fidelity. Free text is never blocked because it doesn't fit a category. Persist feedback before generation. Next round references the selected previous round and saved factors, explains what changed, respects rejected items and tests uncertainty rather than mechanically concatenating likes.

Approval is an explicit user action against a specific immutable round and relevant-input hash (not incidental navigation revision). No maximum round count or automatic confidence-based approval. History can be revisited; reapproval required after material edits. Credits/latency may pause the consultation but cannot force a final style. Save/resume from another device must retain all criticism and pending/uncertain operation states.

## R7 — Editorial

Only approved style revision can produce a final editorial. Include coherent palette/garment grammar, construction/fabric/detail guidance, exceptions and why. Show a glamorous illustration distinct from diagnostic boards when generation works. Product sourcing is a separate adapter with current retailer evidence, fetch timestamp and link validation. Only real checked offers are called purchasable; missing sizes/prices are unknown. Do not fetch arbitrary user/model URLs without validation. Keep a style-only editorial if sourcing unavailable, clearly labelled as such.

Each suggested piece must satisfy harmony, taste, practicality and wardrobe complementarity individually; not one compensating weighted score. User-stated market/budget/size/occasion/material constraints and existing wardrobe notes inform selection. No affiliate/checkout functionality in hackathon scope.

## R9 — Failure accounting and live-test scope

Before dispatch error: failed_before_dispatch, release reserve. Explicit provider refusal/moderation/schema-invalid response: rejected_result, settle reported usage if trustworthy else full reservation; never assume free. Network/process timeout after dispatch or missing provider ID: uncertain, keep full reserve, release concurrency only on lease expiry, expose status and explicit retry. Completed response: succeeded, settle once. Conservative reconciliation: mark conservatively_settled at reserved amount, retain audit outcome; manual user retry is a new paid operation, never hidden resubmission. A server-generated client request ID is written before dispatch; record provider ID if available. Do not couple provider abort to browser disconnect; await within verified platform duration. Cross-device polling never dispatches.

Keep ordinary test suites incapable of real inference unless explicit RUN_PAID_TESTS=true and the operator development grant/ledger are configured. Concurrency, seventh-round permission, exhaustion, crashes and stale writes use deterministic transport fixtures. Live budget is for one combined calibration/integrated journey and a minimal demo take; reuse valid probe outputs as evidence rather than paying for the same acceptance repeatedly. Qualitative fidelity judged by the user/consenting subject and implementation agent: recognisable face, plausibly preserved figure, intended garment change visible, no major rendering defect mistaken for anatomy. Uncertainty/failure is recorded, not passed.

Development-only provisional reservation must derive from documented finite model/input/output/quality limits at current official prices; arbitrary guesses are not bounds. If the candidate image model exposes no defensible upper bound, choose a documented bounded setting/model or keep its paid probe disabled and report the prerequisite. Measured means size allowances but do not replace conservative request bounds. Pool allocation and actual judge count can be adjusted within50USD; do not promise an unmeasured number of full consultations.

Late-result acceptance: if the original response arrives after lease expiry or conservative settlement, recover valid output only after ownership/deletion/relevant-input checks. Settlement is idempotent: no second debit or second reservation release; financial terminal status and recovered-result availability are separate. If conservatively settled, retain that charge pending protected reconciliation rather than automatically crediting it twice.
